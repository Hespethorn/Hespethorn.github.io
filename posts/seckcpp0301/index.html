秒杀系统高并发优化实战（C++ / Drogon）：3.1 整合 jwt-cpp + Redis 会话：用户注册接口

Created2026-09-21|SeckillCpp
|Word Count:3.8k|Reading Time:15mins

10000 个人抢 100 件商品，最后卖出去 137 件——这句"段子"我们在表设计那篇就破了。但秒杀真正的第一道门，不是库存，是身份：你是谁？你有没有资格抢？如果你连"注册"这一步都把明文密码写进库，那后面无论 Redis 预扣、Lua 原子、MQ 削峰做得再漂亮，用户表一旦泄露就是全裸——所有"高并发安全"都建立在沙滩上。

本文是「秒杀系统（C++ / Drogon）」系列第三章（登录模块）的开篇。配套仓库 seckill-cpp(GitHub: https://github.com/Hespethorn/seckill-cpp)。当前仓库 main 分支仅有阶段一的 SeckillService 与 HealthController，登录模块尚未提交；本文代码将随登录模块首个提交进入仓库，目录规划为 sql/user_schema.sql、src/model/User.h、src/service/UserService.{h,cc}、src/controllers/UserController.{h,cc}，路由在 src/main.cc 注册。所有方案均为原创、不依赖任何外部教程。

一、注册接口：是什么、坑在哪、本质一句话

是什么：用户注册接口 = 把"账号（手机号 + 密码）"安全地落库，并为后续登录签发 Token 准备好身份基础。它是整个鉴权链路的"建身份"环节，本身不发 Token（Token 留给登录）。

坑在哪：

  • 明文密码：直接 INSERT password=用户输入，一旦拖库，所有账号裸奔。这是最不该犯的错。
  • 弱哈希：用 MD5(password) 甚至不加盐，彩虹表一秒反查；用固定 salt 等于没加盐。
  • 查重与并发：两个请求同时用同一手机号注册，没唯一索引就会插出两条——后面"一人一单"的资格校验全崩。
  • "无状态 JWT"假象：很多人以为 JWT 无状态就够，但 JWT 一旦签发无法主动吊销（改密码/封号后旧 Token 仍有效），必须有一层可吊销的会话态。

本质一句话：注册接口的本质是"安全地建立账号身份"——密码永远不落明文，会话用 Redis 做可吊销的权威态、JWT 只做不可伪造的凭证。

二、用户表设计

密码哈希用 PBKDF2-HMAC-SHA256，派生长度 32 字节 → hex 编码 64 字符；salt 16 字节 → hex 32 字符。字段定长 CHAR 比 VARCHAR 更省心，也避免长度漂移。

uk_phone 是唯一索引，不只是为了查重快，更是最后一道并发防线：即使应用层查重有竞态，数据库的唯一约束会让第二个 INSERT 直接报 ER_DUP_ENTRY，绝不会插出两条。

三、密码哈希：自实现 PBKDF2（OpenSSL），不引第三方 bcrypt 库

C++ 没有 Spring Security 的 BCrypt，但 OpenSSL 自带工业级 KDF。我选 PBKDF2-HMAC-SHA256 而非直接引 bcrypt-cpp，理由是：依赖更少（OpenSSL 本就是 Drogon/Redis 的底层依赖，几乎必然在场）、可调迭代次数对抗硬件升级、算法透明可审计。代价是要自己管好 salt 与 hex 编码——而这恰恰是本系列想讲透的"自实现功力"。

C++ 细节：RAND_bytes 来自 OpenSSL 的 CSPRNG，比 std::rand() 安全得多——后者是线性同余、可预测，拿来做 salt 等于给攻击者减难度。salt 与哈希分离存储，验证时重新派生比对，绝不在库里存"明文密码 + 一次性比较"。

四、UserService::registerUser：查重 → 哈希 → 落库

沿用本仓库既有风格：服务层只做业务，不碰 HTTP；回调语义统一 (bool ok, string msg)。Drogon 的 DbClient 用流式 >> 接"成功回调 / 异常回调"——SELECT 查到行走第一个回调，查不到（抛 DrogonDbException）走第二个，正好用来判断"手机号是否已注册"。

并发保险：即使两个相同手机号请求在 SELECT 处竞态都"查不到"，第二个 INSERT 也会撞 uk_phone 唯一索引报错，掉进 DB_ERROR 分支——应用层查重是快路径，数据库唯一约束是兜底，两层都不会放过重复注册。

五、UserController + 路由注册

本仓库控制器不继承 HttpController（Drogon v1.9.10 起对带依赖注入、无默认构造的 HttpController 子类调 registerController 会静态断言失败），改为在 main.cc 用 registerHandler 手动挂路由，lambda 转交给实例。注册接口完整套用这套已验证的模式。

六、Redis 会话的"可吊销层"设计（为登录铺垫，注册不发 Token）

注册只建身份、不发 Token——Token 是登录成功后的凭证。但我们要现在就把会话层的契约定下来，否则登录代码会反过来改表结构。设计要点：

  • JWT 只做凭证，不做权威态：jwt-cpp 签发 sub=userId, exp, jti，客户端每次请求带在 Authorization 头。JWT 本身无状态、无法吊销。
  • Redis 做权威态：登录成功后写 sess:{jti} → userId，设 TTL = Token 有效期。jti 是 JWT 唯一 ID。
  • 吊销 = 删 Redis key：改密码/封号时 DEL sess:{jti}，旧 Token 即使未过期，网关校验 EXISTS sess:{jti} 失败即拒绝——可吊销性由此而来。
  • Key 规范：sess:{jti}，value = userId（字符串），EXPIRE 与 JWT 的 exp 对齐。

为什么注册不发 Token：注册成功立刻发 Token 等于"建完身份马上给进门钥匙"，既违反最小权限（注册接口不该隐含登录态），也让"注册即登录"成为刷号脚本的便利通道。身份与凭证在时序上分离，是安全设计的基本纪律。

功能抉择（本篇核心权衡）

① 为什么自实现 jwt-cpp + Redis 会话，而不套 SaToken / Spring Security？
本系列是 C++ 实战记录，Java 生态的 SaToken/Spring Security 在 C++ 里没有对等物。自实现 JWT 签发（jwt-cpp）+ Redis 可吊销会话，把"凭证不可伪造"和"会话可吊销"两件事拆开各司其职，既贴合 C++ 技术栈，也把鉴权链路每一行都摊开讲透——代价是多写几百行基础设施代码，换来对安全语义的完全掌控。

② 为什么密码哈希选 PBKDF2(OpenSSL) 而非直接引 bcrypt 库？
OpenSSL 是 Drogon/Redis/hiredis 的底层依赖，几乎必然在场，引 bcrypt-cpp 是额外一项依赖与编译面；PBKDF2 算法公开可审计、迭代次数随硬件升级上调即可，没有"库停更就裸奔"的风险。代价是自己管理 salt 生成与 hex 编码，而这正是本系列想练的底层功力。

③ 为什么注册不发 Token，把"身份"和"凭证"在时序上分开？
注册只回答"你是谁"，登录才回答"你现在能进门"。注册即发 Token 既违反最小权限，又给刷号脚本开了"注册即得会话"的便利。分两步后，登录模块才能独立引入风控（验证码、错误次数限制），注册接口保持纯粹的"建身份"。

④ 为什么 Redis 会话要做"可吊销层"，而不满足于无状态 JWT？
JWT 无状态意味着签发后服务端无法主动失效，封号/改密后的旧 Token 仍可能被滥用。用 Redis 的 sess:{jti} 作为权威态，吊销 = 删 key，一行命令解决"无法踢人"的硬伤。代价是多一次 Redis 查询（网关每次请求 EXISTS），但相比安全收益微不足道，且 Redis 单实例轻松扛百万 QPS。

小结

  • 注册接口的本质是安全地建立账号身份：明文密码绝不落库，PBKDF2 加盐哈希是底线。
  • 查重靠应用层快路径 + uk_phone 唯一索引兜底双层防护，并发下也不会插重。
  • 密码哈希选 PBKDF2-HMAC-SHA256（OpenSSL 自带），依赖少、算法透明、迭代可调。
  • 会话采用 JWT（凭证，不可伪造）+ Redis（权威态，可吊销） 双层模型，注册不发 Token，身份与凭证时序分离。
  • 控制器沿用本仓库非 HttpController + registerHandler 的已验证模式，与 SeckillController 完全对齐。
