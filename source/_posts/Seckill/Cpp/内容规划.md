## 一、为什么要做秒杀系统（7 大业务挑战，语言无关）

秒杀是互联网大厂面试高频考点，也是最能体现高并发架构设计能力的实战项目。需逐个攻克：

1. **瞬时高并发流量**：活动开始请求量达平时几十~上百倍，连接 / 数据库被耗尽。
2. **库存超卖**：10000 人抢 100 件，如何不多卖。
3. **重复下单**：同一用户多次秒杀成功，如何防止。
4. **黄牛刷单**：脚本 / 机器人 / 多账号抢购，如何保公平。
5. **服务雪崩**：下游订单 / 支付慢导致调用方资源占满，级联故障。
6. **数据一致性**：Redis 预减 + MQ 异步下单 + DB 最终扣减，如何不丢不一致。
7. **系统可扩展性**：用户量 / 活动规模增长，如何水平扩展。

> 本系列视角：以上每个坑都当成一次**功能抉择**来讲——不只给"怎么解"，更给"为什么选它、为此放弃了什么"。例如超卖，乐观锁 / 悲观锁 / SQL 条件判断各有代价，要讲清取舍而非只甩一句"用乐观锁"。

## 二、架构演进路线（4 阶段：50 QPS → 30000+ QPS，C++ 实现）

```
阶段一  基础秒杀系统（Drogon + MySQL 直连）        ~50 QPS
  ↓ 引入 redis-plus-plus 缓存（读优化 + 库存预热）
阶段二  缓存层 Redis                               ~数千 QPS
  ↓ 引入 AMQP-CPP（异步下单 + 削峰填谷）
阶段三  消息队列削峰填谷                            ~万级 QPS
  ↓ 微服务拆分 + 自实现服务治理（brpc / etcd / 令牌桶）
阶段四  微服务 + 服务治理                          ~30000+ QPS
```

> 各阶段瓶颈与解法，详见开篇《专栏介绍》的内联 SVG（已标注 C++ 技术栈）。
