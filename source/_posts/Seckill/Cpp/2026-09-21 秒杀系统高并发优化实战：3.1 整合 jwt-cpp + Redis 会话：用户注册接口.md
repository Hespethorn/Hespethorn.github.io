10000 个人抢 100 件商品，最后卖出去 137 件——这句"段子"我们在表设计那篇就破了。但秒杀真正的第一道门，不是库存，是**身份**：你是谁？你有没有资格抢？如果你连"注册"这一步都把明文密码写进库，那后面无论 Redis 预扣、Lua 原子、MQ 削峰做得再漂亮，用户表一旦泄露就是全裸——所有"高并发安全"都建立在沙滩上。

> 本文是「秒杀系统（C++ / Drogon）」系列第三章（登录模块）的开篇。配套仓库 `seckill-cpp`(GitHub: https://github.com/Hespethorn/seckill-cpp)。当前仓库 main 分支仅有阶段一的 `SeckillService` 与 `HealthController`，登录模块尚未提交；本文代码将随登录模块首个提交进入仓库，目录规划为 `sql/user_schema.sql`、`src/model/User.h`、`src/service/UserService.{h,cc}`、`src/controllers/UserController.{h,cc}`，路由在 `src/main.cc` 注册。所有方案均为原创、不依赖任何外部教程。

## 一、注册接口：是什么、坑在哪、本质一句话

**是什么**：用户注册接口 = 把"账号（手机号 + 密码）"安全地落库，并为后续登录签发 Token 准备好身份基础。它是整个鉴权链路的"建身份"环节，本身不发 Token（Token 留给登录）。

**坑在哪**：

- **明文密码**：直接 `INSERT password=用户输入`，一旦拖库，所有账号裸奔。这是最不该犯的错。
- **弱哈希**：用 `MD5(password)` 甚至不加盐，彩虹表一秒反查；用固定 salt 等于没加盐。
- **查重与并发**：两个请求同时用同一手机号注册，没唯一索引就会插出两条——后面"一人一单"的资格校验全崩。
- **"无状态 JWT"假象**：很多人以为 JWT 无状态就够，但 JWT 一旦签发无法主动吊销（改密码/封号后旧 Token 仍有效），必须有一层**可吊销的会话态**。

**本质一句话**：注册接口的本质是"安全地建立账号身份"——**密码永远不落明文**，会话用 Redis 做可吊销的权威态、JWT 只做不可伪造的凭证。

## 二、用户表设计

密码哈希用 `PBKDF2-HMAC-SHA256`，派生长度 32 字节 → hex 编码 64 字符；salt 16 字节 → hex 32 字符。字段定长 `CHAR` 比 `VARCHAR` 更省心，也避免长度漂移。

```sql
-- sql/user_schema.sql
CREATE TABLE `user` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `phone`         VARCHAR(20)  NOT NULL                COMMENT '登录手机号，唯一',
  `password_hash` CHAR(64)     NOT NULL                COMMENT 'PBKDF2-HMAC-SHA256 派生，hex 编码',
  `salt`          CHAR(32)     NOT NULL                COMMENT '16 字节随机 salt，hex 编码',
  `nickname`      VARCHAR(64)  DEFAULT ''              COMMENT '昵称，可空',
  `status`        TINYINT      NOT NULL DEFAULT 1      COMMENT '1=正常 0=禁用',
  `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_phone` (`phone`)                      COMMENT '查重 + 防并发插重的核心约束'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> `uk_phone` 是唯一索引，不只是为了查重快，更是**最后一道并发防线**：即使应用层查重有竞态，数据库的唯一约束会让第二个 INSERT 直接报 `ER_DUP_ENTRY`，绝不会插出两条。

## 三、密码哈希：自实现 PBKDF2（OpenSSL），不引第三方 bcrypt 库

C++ 没有 Spring Security 的 `BCrypt`，但 OpenSSL 自带工业级 KDF。我选 **PBKDF2-HMAC-SHA256** 而非直接引 `bcrypt-cpp`，理由是：依赖更少（OpenSSL 本就是 Drogon/Redis 的底层依赖，几乎必然在场）、可调迭代次数对抗硬件升级、算法透明可审计。代价是要自己管好 salt 与 hex 编码——而这恰恰是本系列想讲透的"自实现功力"。

```cpp
// src/service/password.h（登录模块新增）
#pragma once
#include <string>

// 生成 16 字节密码学安全随机 salt（hex 编码返回）
std::string genSalt(size_t bytes = 16);

// PBKDF2-HMAC-SHA256 派生密钥，返回 hex 字符串
// iterations 视机器性能取 10w~20w：太低易被暴力，太高拖慢登录
std::string pbkdf2Hex(const std::string& password,
                       const std::string& salt,
                       int iterations = 120000,
                       size_t dkLen = 32);
```

```cpp
// src/service/password.cc
#include "password.h"
#include <openssl/evp.h>
#include <openssl/rand.h>
#include <algorithm>
#include <cctype>

std::string genSalt(size_t bytes) {
    std::string out;
    out.resize(bytes);
    RAND_bytes(reinterpret_cast<unsigned char*>(out.data()), static_cast<int>(bytes));
    // 转 hex，便于存 CHAR 字段且无编码歧义
    static const char* hexd = "0123456789abcdef";
    std::string hex;
    hex.reserve(bytes * 2);
    for (unsigned char c : out) {
        hex.push_back(hexd[c >> 4]);
        hex.push_back(hexd[c & 0x0f]);
    }
    return hex; // 长度 = bytes * 2 = 32
}

std::string pbkdf2Hex(const std::string& password,
                      const std::string& salt,
                      int iterations, size_t dkLen) {
    std::string out;
    out.resize(dkLen);
    int rc = PKCS5_PBKDF2_HMAC(
        password.data(), static_cast<int>(password.size()),
        reinterpret_cast<const unsigned char*>(salt.data()),
        static_cast<int>(salt.size()),
        iterations, EVP_sha256(),
        static_cast<int>(dkLen),
        reinterpret_cast<unsigned char*>(out.data()));
    if (rc != 1) return ""; // 极罕见：OpenSSL 初始化失败
    static const char* hexd = "0123456789abcdef";
    std::string hex;
    hex.reserve(dkLen * 2);
    for (unsigned char c : out) {
        hex.push_back(hexd[c >> 4]);
        hex.push_back(hexd[c & 0x0f]);
    }
    return hex; // 长度 = dkLen * 2 = 64
}
```

> **C++ 细节**：`RAND_bytes` 来自 OpenSSL 的 CSPRNG，比 `std::rand()` 安全得多——后者是线性同余、可预测，拿来做 salt 等于给攻击者减难度。salt 与哈希分离存储，验证时重新派生比对，绝不在库里存"明文密码 + 一次性比较"。

## 四、UserService::registerUser：查重 → 哈希 → 落库

沿用本仓库既有风格：服务层只做业务，不碰 HTTP；回调语义统一 `(bool ok, string msg)`。Drogon 的 `DbClient` 用流式 `>>` 接"成功回调 / 异常回调"——`SELECT` 查到行走第一个回调，查不到（抛 `DrogonDbException`）走第二个，正好用来判断"手机号是否已注册"。

```cpp
// src/service/UserService.h（登录模块新增）
#pragma once
#include <drogon/orm/DbClient.h>
#include <functional>
#include <memory>

class UserService {
public:
    explicit UserService(drogon::orm::DbClientPtr client)
        : db_(std::move(client)) {}

    // 回调：(true,"OK") 注册成功 / (false,"PHONE_REGISTERED") 已注册
    //       / (false,"INVALID_PHONE") 格式错 / (false,"DB_ERROR:..") 系统异常
    void registerUser(const std::string& phone,
                      const std::string& password,
                      std::function<void(bool, const std::string&)> &&cb);

private:
    drogon::orm::DbClientPtr db_;
};
```

```cpp
// src/service/UserService.cc
#include "UserService.h"
#include "password.h"
#include <algorithm>
#include <cctype>

void UserService::registerUser(
    const std::string& phone,
    const std::string& password,
    std::function<void(bool, const std::string&)> &&cb) {
    // 1) 入参校验：手机号 1 开头 + 11 位数字（业务上够用，正则可后扩）
    if (phone.size() != 11 || phone[0] != '1' ||
        !std::all_of(phone.begin(), phone.end(), ::isdigit)) {
        cb(false, "INVALID_PHONE");
        return;
    }
    if (password.size() < 6) { // 弱口令从源头拦一道
        cb(false, "WEAK_PASSWORD");
        return;
    }

    // 2) 查重：手机号唯一。查到行 → 已注册；抛异常（无结果）→ 继续
    *db_ << "SELECT id FROM user WHERE phone = ?" << phone >>
        [=](int64_t /*id*/) {
            cb(false, "PHONE_REGISTERED");
        } >>
        [=](const drogon::orm::DrogonDbException& /*e*/) {
            // 视为未注册，继续注册主流程
            std::string salt = genSalt();
            std::string hash = pbkdf2Hex(password, salt);
            if (hash.empty()) { cb(false, "DB_ERROR:hash"); return; }

            // 3) 落库：salt 与 hash 同时写入，INSERT 成功回调无参
            *db_ << "INSERT INTO user (phone, password_hash, salt, status, create_time) "
                    "VALUES (?, ?, ?, 1, NOW())"
                 << phone << hash << salt >>
                [=]() { cb(true, "OK"); } >>
                [=](const drogon::orm::DrogonDbException& e) {
                    cb(false, std::string("DB_ERROR:") + e.what());
                };
        };
}
```

> **并发保险**：即使两个相同手机号请求在 `SELECT` 处竞态都"查不到"，第二个 `INSERT` 也会撞 `uk_phone` 唯一索引报错，掉进 `DB_ERROR` 分支——应用层查重是快路径，数据库唯一约束是兜底，两层都不会放过重复注册。

## 五、UserController + 路由注册

本仓库控制器**不继承 `HttpController`**（Drogon v1.9.10 起对带依赖注入、无默认构造的 `HttpController` 子类调 `registerController` 会静态断言失败），改为在 `main.cc` 用 `registerHandler` 手动挂路由，lambda 转交给实例。注册接口完整套用这套已验证的模式。

```cpp
// src/controllers/UserController.h（登录模块新增）
#pragma once
#include <drogon/HttpController.h>
#include <functional>
#include <memory>
#include "service/UserService.h"

class UserController {
public:
    explicit UserController(std::shared_ptr<UserService> svc)
        : svc_(std::move(svc)) {}
    void registerUser(const drogon::HttpRequestPtr& req,
                      std::function<void(const drogon::HttpResponsePtr&)>&& callback);
private:
    std::shared_ptr<UserService> svc_;
};
```

```cpp
// src/controllers/UserController.cc
#include "UserController.h"
#include <json/json.h>

void UserController::registerUser(
    const drogon::HttpRequestPtr& req,
    std::function<void(const drogon::HttpResponsePtr&)>&& callback) {
    const auto& json = req->getJsonObject(); // v1.9.10 起返回 shared_ptr
    if (!json || !json->isMember("phone") || !json->isMember("password")) {
        Json::Value err;
        err["code"] = 400;
        err["msg"]  = "missing phone/password";
        auto resp = drogon::HttpResponse::newHttpJsonResponse(err);
        resp->setStatusCode(drogon::k400BadRequest);
        callback(resp);
        return;
    }
    const std::string phone = (*json)["phone"].asString();
    const std::string password = (*json)["password"].asString();

    svc_->registerUser(phone, password,
        [callback](bool ok, const std::string& msg) mutable {
            Json::Value root;
            root["code"] = ok ? 0 : 1;
            root["msg"]  = ok ? "success" : msg;
            auto resp = drogon::HttpResponse::newHttpJsonResponse(root);
            if (!ok) resp->setStatusCode(drogon::k409Conflict);
            callback(resp);
        });
}
```

`main.cc` 里挂路由（与 `seckillCtrl` 同款写法）：

```cpp
// src/main.cc（登录模块新增两行）
auto userService = std::make_shared<UserService>(getDbClient());
auto userCtrl    = std::make_shared<UserController>(userService);
app().registerHandler("/api/user/register",
    [userCtrl](const drogon::HttpRequestPtr& req,
               std::function<void(const drogon::HttpResponsePtr&)>&& cb) {
        userCtrl->registerUser(req, std::move(cb));
    },
    {drogon::HttpMethod::Post});
```

## 六、Redis 会话的"可吊销层"设计（为登录铺垫，注册不发 Token）

注册**只建身份、不发 Token**——Token 是登录成功后的凭证。但我们要**现在就把会话层的契约定下来**，否则登录代码会反过来改表结构。设计要点：

- **JWT 只做凭证，不做权威态**：`jwt-cpp` 签发 `sub=userId, exp, jti`，客户端每次请求带在 `Authorization` 头。JWT 本身无状态、无法吊销。
- **Redis 做权威态**：登录成功后写 `sess:{jti} → userId`，设 TTL = Token 有效期。`jti` 是 JWT 唯一 ID。
- **吊销 = 删 Redis key**：改密码/封号时 `DEL sess:{jti}`，旧 Token 即使未过期，网关校验 `EXISTS sess:{jti}` 失败即拒绝——可吊销性由此而来。
- **Key 规范**：`sess:{jti}`，value = `userId`（字符串），`EXPIRE` 与 JWT 的 `exp` 对齐。

```cpp
// 登录阶段实现（redis-plus-plus），此处先定契约，注册篇不实际签发
sw::redis::Redis redis("tcp://127.0.0.1:6379");
redis.setex("sess:" + jti, ttlSeconds, std::to_string(userId)); // 登录成功写会话
// 网关校验：if (!redis.exists("sess:" + jti)) reject();  // 可吊销
```

> 为什么注册不发 Token：注册成功立刻发 Token 等于"建完身份马上给进门钥匙"，既违反最小权限（注册接口不该隐含登录态），也让"注册即登录"成为刷号脚本的便利通道。身份与凭证在时序上分离，是安全设计的基本纪律。

## 八、两张对比表

**表 1：密码存储方案对比**

| 方案 | 抗彩虹表 | 抗暴力破解 | 加盐 | 评价 |
|------|---------|-----------|------|------|
| 明文 | ✗ | ✗ | ✗ | 拖库即全裸，绝不可取 |
| MD5(密码) | ✗ | ✗ | ✗ | 秒级反查，已淘汰 |
| MD5(密码+salt)，salt 固定 | △ | ✗ | 弱 | 固定 salt = 全库共用，仍可被批量跑 |
| bcrypt | ✓ | ✓ | ✓ | 自带 salt + 慢哈希，工业标准但需引库 |
| **PBKDF2-HMAC-SHA256（本文）** | ✓ | ✓ | ✓ | 算法透明、依赖少（OpenSSL 自带）、迭代可调 |

**表 2：会话模型对比**

| 模型 | 可吊销 | 实现复杂度 | 适用 |
|------|--------|-----------|------|
| 纯无状态 JWT | ✗（改密/封号后仍有效） | 低 | 短期、低风险 API |
| **JWT + Redis 会话（本文）** | ✓（DEL key 即吊销） | 中 | 秒杀等需强管控场景 |
| 纯 Redis Session（不签发 JWT） | ✓ | 低 | 单体，无跨服务诉求 |

## 功能抉择（本篇核心权衡）

**① 为什么自实现 jwt-cpp + Redis 会话，而不套 SaToken / Spring Security？**
本系列是 C++ 实战记录，Java 生态的 SaToken/Spring Security 在 C++ 里没有对等物。自实现 JWT 签发（jwt-cpp）+ Redis 可吊销会话，把"凭证不可伪造"和"会话可吊销"两件事拆开各司其职，既贴合 C++ 技术栈，也把鉴权链路每一行都摊开讲透——代价是多写几百行基础设施代码，换来对安全语义的完全掌控。

**② 为什么密码哈希选 PBKDF2(OpenSSL) 而非直接引 bcrypt 库？**
OpenSSL 是 Drogon/Redis/hiredis 的底层依赖，几乎必然在场，引 `bcrypt-cpp` 是额外一项依赖与编译面；PBKDF2 算法公开可审计、迭代次数随硬件升级上调即可，没有"库停更就裸奔"的风险。代价是自己管理 salt 生成与 hex 编码，而这正是本系列想练的底层功力。

**③ 为什么注册不发 Token，把"身份"和"凭证"在时序上分开？**
注册只回答"你是谁"，登录才回答"你现在能进门"。注册即发 Token 既违反最小权限，又给刷号脚本开了"注册即得会话"的便利。分两步后，登录模块才能独立引入风控（验证码、错误次数限制），注册接口保持纯粹的"建身份"。

**④ 为什么 Redis 会话要做"可吊销层"，而不满足于无状态 JWT？**
JWT 无状态意味着签发后服务端无法主动失效，封号/改密后的旧 Token 仍可能被滥用。用 Redis 的 `sess:{jti}` 作为权威态，吊销 = 删 key，一行命令解决"无法踢人"的硬伤。代价是多一次 Redis 查询（网关每次请求 `EXISTS`），但相比安全收益微不足道，且 Redis 单实例轻松扛百万 QPS。

## 小结

- 注册接口的本质是**安全地建立账号身份**：明文密码绝不落库，PBKDF2 加盐哈希是底线。
- 查重靠**应用层快路径 + `uk_phone` 唯一索引兜底**双层防护，并发下也不会插重。
- 密码哈希选 **PBKDF2-HMAC-SHA256（OpenSSL 自带）**，依赖少、算法透明、迭代可调。
- 会话采用 **JWT（凭证，不可伪造）+ Redis（权威态，可吊销）** 双层模型，注册不发 Token，身份与凭证时序分离。
- 控制器沿用本仓库**非 `HttpController` + `registerHandler`** 的已验证模式，与 `SeckillController` 完全对齐。
