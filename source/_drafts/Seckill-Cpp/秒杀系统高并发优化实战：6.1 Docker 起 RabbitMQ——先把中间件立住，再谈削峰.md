阶段二把**读**链路做到了 L1 本地 LRU → L2 Redis → L3 MySQL，读 QPS 实测 ×1.40/×1.44。但洪峰真正压死系统的从来不是读——是**写**。4.7 的基线已经把根因钉死了：`seckill_sku` 单行上的行锁把所有下单请求串行化，QPS 卡在 371。缓存救不了它，因为库存的真相源只在 MySQL。

阶段三要做的事只有一件：**把「用户点下单」和「MySQL 扣库存落订单」这两件事在时间上拆开**。中间隔一层消息队列，HTTP 线程只负责"收下这个请求并承诺处理"，慢动作交给消费者慢慢消化。这一篇是阶段三的第一块砖：先把 RabbitMQ 用 Docker 立起来，把交换机、队列、路由键这套**契约**定死，再谈代码。

> 本文是「秒杀系统（C++ / Drogon）」系列第六章第一篇（阶段三开篇）。配套资产（本文新增，随 `v0.3.x` 落地）：`docker/rabbitmq/docker-compose.yml`、`docker/rabbitmq/rabbitmq.conf`、`docker/rabbitmq/definitions.json`、`scripts/mq-up.sh`、`scripts/mq-smoke.sh`，以及 `config.json` 新增 `custom_config.mq` 段。仓库当前最新 tag `v1.0.0`（阶段二），阶段三代码尚未打 tag。真实环境：WSL Ubuntu（i7-14650HX）+ Docker。

## 一、MQ 削峰是什么、坑在哪、本质一句话

- **是什么**：下单接口不再同步等 MySQL 事务提交，而是把"谁买了什么"这条消息丢进队列立刻返回；后台消费者按自己的节奏（受 MySQL 行锁上限约束）逐条落库。**请求速率**和**落库速率**解耦。
- **坑（最容易被忽略的三条）**：
  1. **消息丢了怎么办** —— 生产者发完就返回，Broker 崩了这条消息就没了，用户以为抢到了实际没订单；
  2. **消息重复了怎么办** —— 网络抖动触发重发，同一条消息被消费两次，库存扣两遍；
  3. **用户怎么知道抢没抢到** —— 异步之后 HTTP 响应里没有最终结果，前端必须另开一条查询通道。
- **本质一句话**：**MQ 削峰不提升系统的总吞吐上限，它只是把"瞬时洪峰"摊平成"匀速水流"，代价是引入了「消息可靠性」和「结果可见性」两个全新的复杂度——你用一个瓶颈换了两个问题。**

认清这一点很重要：如果消费者最终还是一条条打在同一行 `seckill_sku` 上，行锁的**总吞吐上限**不会变。MQ 让你不被冲垮，但不让你变快——真正突破上限要等到阶段四把库存搬到 Redis 用 Lua 原子预扣。阶段三解决的是"活下来"，不是"更快"。

## 二、功能抉择（一）：为什么是 RabbitMQ，不是 Kafka / Redis Stream / 自写队列

这是本阶段第一个、也是最重要的取舍。四条路摆在面前：

| 方案 | 匹配度 | 选它的理由 | 放弃的代价 |
| --- | --- | --- | --- |
| **RabbitMQ（选）** | 高 | AMQP 语义完整：per-message **手动 ACK**、**publisher confirm**、**死信队列**、**prefetch 限流**——秒杀要的可靠性原语它全有，且单条延迟百微秒级 | 单机吞吐约数万/秒，低于 Kafka 一个量级；Erlang 栈，运维排查成本略高 |
| Kafka | 中 | 吞吐百万级，分区顺序好 | 语义是"日志"不是"队列"：没有 per-message ACK、没有原生死信；消费位点由 consumer group 管，做"消费失败重投"要自己造轮子。秒杀的消息量（一次活动几十万条）**根本用不上它的吞吐**，却要吃下它缺失的可靠性语义 |
| Redis Stream | 中 | 项目里 Redis 已经在跑（阶段二），零新增组件 | 可靠性弱一档：AOF 默认每秒刷盘可能丢一秒数据；没有原生死信；且会把"缓存"和"消息"两种 SLA 完全不同的流量压在同一个 Redis 实例上，缓存抖动直接带崩下单链路 |
| 自写无锁队列 | 低 | 极致可控，无外部依赖 | 进程内队列**等于没有解耦**：进程一崩消息全丢，也没法多实例扩展。分布式场景下自写队列 = 自研一个 Kafka，是明确的过度设计 |

**决策**：选 RabbitMQ。理由是**秒杀的瓶颈从来不是 MQ 的吞吐**（一次活动几十万条消息，RabbitMQ 单节点绰绰有余），而是**消息不能丢、不能重复扣、失败能重投**——这三点恰好是 AMQP 协议的原生能力，用 Kafka 反而要自己补齐。

**放弃的代价**明说：接受 RabbitMQ 单机数万/秒的吞吐天花板，以及多一个 Erlang 进程要运维。在"消息量不大但绝不能错"的场景里，这笔交易划算。

## 三、Docker 起 RabbitMQ：一份能直接跑的 compose

选 `3.13-management-alpine`——带 management 插件，省得再手动 `rabbitmq-plugins enable`。注意用 `docker compose`（v2 插件）而不是老 `docker-compose`；下面的文件刻意**不写 `version:` 键**，v2 会把它当废弃字段刷警告。

```yaml
# docker/rabbitmq/docker-compose.yml
services:
  rabbitmq:
    image: rabbitmq:3.13-management-alpine
    container_name: seckill-rabbitmq
    hostname: seckill-mq
    ports:
      - "5672:5672"     # AMQP 协议端口（业务链路）
      - "15672:15672"   # Management HTTP API / UI（观测与冒烟，不进主链路）
    environment:
      RABBITMQ_DEFAULT_USER: seckill
      RABBITMQ_DEFAULT_PASS: seckill_pass
      RABBITMQ_DEFAULT_VHOST: /seckill
    volumes:
      - ./data:/var/lib/rabbitmq
      - ./rabbitmq.conf:/etc/rabbitmq/rabbitmq.conf:ro
      - ./definitions.json:/etc/rabbitmq/definitions.json:ro
    ulimits:
      nofile:
        soft: 65536
        hard: 65536
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
      interval: 10s
      timeout: 5s
      retries: 10
    restart: unless-stopped
```

几个不是"抄来就能用"的细节，每一个都对应一个真实会踩的坑：

- **`ulimits.nofile`**：默认 1024。秒杀场景下 Drogon 用连接池连过来，加上消费者长连接，文件描述符很快见底，症状是"连接随机断"。
- **`RABBITMQ_DEFAULT_VHOST`**：用独立 vhost `/seckill` 而不是默认 `/`。这台机器上 Redis 里还住着 `sess:`/`sms:`/`login:` 等登录态数据，vhost 是 RabbitMQ 侧等价的**命名空间隔离**——将来若复用同一 Broker，权限和队列都不会互相污染。
- **挂载 `definitions.json`**：把 exchange/queue/binding 的声明**写进文件、随容器启动自动导入**。这样重建容器后拓扑自动恢复，不用手工点 UI，也不怕"环境漂移"。
- **`healthcheck`**：`docker compose up -d` 返回成功 ≠ 服务可用。Erlang 节点启动要几秒到十几秒，脚本里必须轮询健康态而不是 `sleep 10` 硬等。

配置文件两行，把 definitions 打开、把磁盘保护阈值调低（本地开发机磁盘小，默认 50MB 告警很吵）：

```ini
# docker/rabbitmq/rabbitmq.conf
load_definitions = /etc/rabbitmq/definitions.json
disk_free_limit.absolute = 1GB
```

**交换机类型**：选 `direct` 而非 `topic`/`fanout`。理由是当前只有一个消费者、一种消息，direct 的**精确匹配**语义最直白、路由开销最低（`topic` 要做模式匹配，`fanout` 直接广播丢弃 routing key）。现在选 direct **不等于**锁死将来——exchange 不能改类型，但可以新增 `seckill.order.topic` 并重新绑定，成本可接受。

**队列类型**：`classic` + `durable` + 消息 `persistent`，而不是 `quorum`。

| | classic（选） | quorum | 说明 |
| --- | --- | --- | --- |
| 一致性 | 单节点，无副本 | Raft 多数派复制 | quorum 要奇数节点（≥3），单节点部署拿不到任何 HA 收益 |
| 延迟 | 低 | 高（每条消息要走一次 Raft 提交） | 单节点下 quorum 是**纯亏**：多付了复制开销却没有副本 |
| 消息不丢 | 依赖持久化 + 手动 ACK | 强保证 | 单节点下两者都会因磁盘损坏丢数据，真正的高可用靠集群而非队列类型 |

**决策**：本地/单节点阶段用 classic；等到真的上多节点集群，再把队列类型换成 quorum（到时是运维切换，业务代码零改动——这正是 AMQP "声明即契约"的好处）。

## 五、声明写进 definitions.json：拓扑即代码

```json
{
  "rabbit_version": "3.13",
  "vhosts": [{ "name": "/seckill" }],
  "exchanges": [
    {
      "name": "seckill.order.direct",
      "vhost": "/seckill",
      "type": "direct",
      "durable": true,
      "auto_delete": false,
      "internal": false,
      "arguments": {}
    }
  ],
  "queues": [
    {
      "name": "seckill.order.create",
      "vhost": "/seckill",
      "durable": true,
      "auto_delete": false,
      "arguments": {}
    }
  ],
  "bindings": [
    {
      "source": "seckill.order.direct",
      "vhost": "/seckill",
      "destination": "seckill.order.create",
      "destination_type": "queue",
      "routing_key": "order.create",
      "arguments": {}
    }
  ]
}
```

三个字段值得单独点名，它们直接对应"消息不能丢"：`durable: true`（队列元数据落盘，Broker 重启队列还在）、将来消息体上的 `delivery_mode: 2`（消息体落盘）、以及 6.8 要接的**手动 ACK**（消费成功才删）。**只把队列设成 durable 而消息不设 persistent，Broker 重启后队列还在、消息没了**——这是最经典的半吊子可靠。

顺带说下项目里的约定：routing key 统一 `order.create` 这种 `<域>.<动作>` 两段式。现在只有一个 key 显得多余，但等到 7.6/7.7 做库存回补、8.x 做死信重投时，新增 key 无需动交换机。

## 六、验证：五步冒烟，先把链路摸通

这一步的意义在于——**在写任何 C++ 代码之前先用 HTTP 把整条链路走通**。如果连"发一条消息能被取到"都不成立，后面排查就会在"是 AMQP-CPP 用错了还是拓扑错了"之间反复横跳。

```bash
# scripts/mq-up.sh
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/../docker/rabbitmq"
docker compose up -d
# healthcheck 通过才算起好，不能靠 sleep 硬等
for i in $(seq 1 30); do
  if [ "$(docker inspect -f '{{.State.Health.Status}}' seckill-rabbitmq)" = "healthy" ]; then
    echo "rabbitmq healthy"; exit 0
  fi
  sleep 2
done
echo "rabbitmq 启动超时" >&2; exit 1
```

```bash
# scripts/mq-smoke.sh —— 声明 → 发一条 → 取一条 → 看深度
#!/usr/bin/env bash
set -euo pipefail
API=http://127.0.0.1:15672
AUTH=seckill:seckill_pass
V=%2Fseckill          # vhost "/seckill" 的 URL 编码
EX=seckill.order.direct
Q=seckill.order.create

echo "[1/4] whoami"
curl -sf -u "$AUTH" "$API/api/whoami"; echo

echo "[2/4] 幂等声明 exchange / queue / binding"
curl -sf -u "$AUTH" -X PUT -H 'content-type: application/json' \
  -d '{"type":"direct","durable":true,"auto_delete":false,"arguments":{}}' \
  "$API/api/exchanges/$V/$EX" >/dev/null
curl -sf -u "$AUTH" -X PUT -H 'content-type: application/json' \
  -d '{"durable":true,"auto_delete":false,"arguments":{}}' \
  "$API/api/queues/$V/$Q" >/dev/null
curl -sf -u "$AUTH" -X POST -H 'content-type: application/json' \
  -d '{"routing_key":"order.create","arguments":{}}' \
  "$API/api/bindings/$V/e/$EX/q/$Q" >/dev/null

echo "[3/4] 发一条持久化消息（delivery_mode=2）"
curl -sf -u "$AUTH" -X POST -H 'content-type: application/json' \
  -d '{"properties":{"delivery_mode":2},"routing_key":"order.create",
       "payload":"{\"skuId\":1001,\"userId\":7}","payload_encoding":"string"}' \
  "$API/api/exchanges/$V/$EX/publish"; echo

echo "[4/4] 取一条（ackmode=ack_requeue_false 表示取走即确认）"
curl -sf -u "$AUTH" -X POST -H 'content-type: application/json' \
  -d '{"count":1,"ackmode":"ack_requeue_false","encoding":"auto"}' \
  "$API/api/queues/$V/$Q/get"; echo
```

`[3/4]` 返回的 `{"routed":true}` 是第一个关键信号——**routed 为 false 说明 binding 没生效**，消息会被静默丢弃，这是 AMQP 新手最常见的"消息凭空消失"。`[4/4]` 能取回同一个 payload，说明"生产 → exchange → queue → 消费"闭环成立。

容器内用 `rabbitmqctl` 做交叉验证（HTTP API 说谎时以它为准）：

```bash
docker exec seckill-rabbitmq rabbitmqctl list_exchanges -p /seckill name type durable
docker exec seckill-rabbitmq rabbitmqctl list_queues   -p /seckill name messages durable
docker exec seckill-rabbitmq rabbitmqctl list_bindings -p /seckill source_name destination_name routing_key
```

预期输出里必须能看到 `seckill.order.direct direct true`、`seckill.order.create 0 true`、以及一行 routing_key 为 `order.create` 的绑定。

## 七、config.json 新增 mq 段（本文新增）

Drogon 的配置体系是 `custom_config` 自由段，用 `app().getCustomConfig()` 读取。这里先把连接参数收进来，**只做解析不发消息**——真正的连接代码在 6.2：

```json
{
  "custom_config": {
    "mq": {
      "host": "127.0.0.1",
      "port": 5672,
      "vhost": "/seckill",
      "user": "seckill",
      "password": "seckill_pass",
      "exchange": "seckill.order.direct",
      "queue": "seckill.order.create",
      "routing_key": "order.create",
      "prefetch": 64
    }
  }
}
```

`prefetch: 64` 先占位：它决定"消费者最多同时挂着多少条未 ACK 的消息"，是 6.7 削峰的核心旋钮。这里先写死一个值，避免 6.2 接 AMQP-CPP 时把魔法数字散落进代码。

> 注意：`password` 明文入配置是本地开发的妥协，生产应走环境变量或配置中心（阶段四的 etcd）。这一点在 2.5 做配置基础设施时就定下了原则——**配置里可以有默认值，但敏感值必须能被外部覆盖**。

## 八、小结

| 项 | 结论 |
| --- | --- |
| 本质 | MQ 削峰**不提升总吞吐上限**，只把洪峰摊平成匀速水流；代价是新增"消息可靠性"与"结果可见性"两个复杂度 |
| 选型 | RabbitMQ 而非 Kafka/Redis Stream/自写队列——秒杀不缺吞吐，缺的是手动 ACK / confirm / 死信这些 AMQP 原生可靠性语义 |
| 部署 | `docker compose`（v2）+ `3.13-management-alpine`；`ulimits.nofile` 提到 65536；独立 vhost `/seckill`；healthcheck 轮询而非 sleep |
| 契约 | exchange `seckill.order.direct`(direct/durable) → routing key `order.create` → queue `seckill.order.create`(classic/durable) |
| 拓扑即代码 | exchange/queue/binding 写进 `definitions.json`，随容器启动导入，杜绝环境漂移 |
| 队列类型 | 单节点选 classic（quorum 在无副本时纯亏延迟）；上集群再切 quorum，业务代码零改动 |
| 可靠性三件套 | durable 队列 + `delivery_mode:2` 持久化消息 + 手动 ACK（6.8）——**只做一半等于没做** |
| 验证 | `routed:true` 是路由生效的唯一硬信号；`rabbitmqctl` 交叉核对；代码之前先跑通 HTTP 冒烟 |

> 🐾 核心三句话：**MQ 削峰买的不是速度，是"不被冲垮"——它把入口的尖峰变成了出口的匀速，而行锁的总吞吐上限一分没涨；选型上秒杀缺的从来不是吞吐而是可靠性语义，所以选 RabbitMQ 拿它原生的手动 ACK / confirm / 死信，而不是用 Kafka 去补这些轮子；而在写任何 C++ 代码之前，先用 HTTP 把"发一条能被取到"跑通——拓扑错了代码再对也是白搭。**
